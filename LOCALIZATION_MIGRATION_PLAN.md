# Phase 4A copy coverage and staged migration plan

This is an audit and future-work plan, not authorization to migrate screens or activate Arabic. Public language remains English/LTR and the Language Settings row remains read-only. Appearance remains the user-tested saved Light/Dark/System implementation. User-reported Phase 3C Android evidence covers selection, restart persistence, Cancel and live System appearance.

## Inventory evidence and limits

`LOCALIZATION_COPY_INVENTORY.json` records every one of the **157 TypeScript/TSX source files**, its SHA-256, local import dependencies, conservative route reachability, and line-numbered copy candidates. It scans all **22 Expo Router route/layout files** as roots and includes native/web source variants. Its dependency closure contains **150 files**. There are **1,344 candidates in 111 files** (including 7 candidates in four unreachable starter components); **1,337 candidates in 107 files** are in the conservative reachable closure. These are candidate occurrences, not unique messages or a claim that every candidate should be translated.

| Source area | Files scanned | Files with candidates | Candidate occurrences |

| Routes/layouts | 22 | 17 | 364 |

| Data/metadata/storage | 26 | 23 | 284 |
| Hooks/providers | 19 | 9 | 41 |
| Domain/display utilities | 20 | 14 | 156 |
| Theme constants | 2 | 0 | 0 |
| Localization infrastructure | 9 | 0 | 0 (intentionally excluded from copy extraction) |

Regenerate the artifact with `node scripts/audit-localization.mjs --write`. Without `--write`, the script prints JSON and performs no writes. Tests check reproducibility and source hashes. It reads source files only, never storage, a phone, private backups or runtime user content.

Extraction catches JSX text, visible/accessibility props, prose strings, templates, metadata and errors. False positives include route-like values, developer errors, URLs and technical identifiers. It can miss lower-case single-word fragments, computed JSX, arbitrary dynamic imports, dependency-provided copy and OS-owned text. Type-only imports can overstate reachability. A zero-candidate file is not certified copy-free: generic components may display labels passed from metadata or a parent. The feature review below covers those indirect producers and establishes the future manual closure checks.

The current infrastructure contains **147 fixed bilingual labels** and **26 parameterized bilingual messages**, including **11 cardinal plural messages** with all six Arabic forms. This is a semantic seed catalog, **not full screen or string coverage**; no percentage of the 1,344 occurrences is claimed as translated. Labels are contextual drafts: future migration must compare the exact original English sentence and meaning rather than globally replacing equal strings. Arabic wording requires native review.

## Safe migration sequence (future approval required)

1. **Catalog contracts and English-only migration pilots.** Freeze reviewed key/parameter meanings, add exact missing English/Arabic pairs per feature, and retain English/LTR while migrating only common controls, navigation labels and Settings/Profile presentation. Keep appearance reducer/store/theme identity unchanged. Snapshot the exact approved English messages; do not globally replace strings or move domain state into catalogs.
2. **Forms and validation boundaries.** Habits, Goals, Routines and Profile together with their pickers, error descriptors and accessibility labels. Preserve existing validation decisions and field association. If numeric-input normalization is adopted, apply only to numeric fields before the unchanged parser, with separately reviewed tests for Arabic/Eastern digits and rejected decimal/grouping input. Never normalize names, units, notes, filenames or machine date keys.
3. **Today and routines progress.** Migrate greetings, counts, states, summaries and control announcements as complete sentences. Keep done/total/due facts, midnight behavior, save queues and routine order unchanged. Treat existing demo content as user content once saved.
4. **Goals detail/Insights.** Add descriptor/fact adapters around current label-building code, preserving aggregation inputs and outputs. Localize numbers/dates only where displayed; chart ordering, scheduled opportunities and unknown/provisional semantics remain separate from language. Test date ranges across year boundaries and DST without UTC parsing of local keys.
5. **Achievements.** Add ID-keyed presentation metadata and complete data-note sentences. Test unknown IDs, acknowledgement save/retry, provisional history, current schedules and saved awards. No award recomputation for locale changes.
6. **Backup/recovery last, with dedicated safety review.** First map operation/error codes and descriptor parameters at presentation boundaries; cover every runtime/file/schema/checksum/size/readability/restore/recovery path. Compare exact exported backup/journal bytes and recovery control flow. Keep domain safety classification before message rendering and maintain startup access when preferences cannot load. Preserve native/share/save outcome distinctions.
7. **Closure audit before activation.** Rerun inventory, reconcile each candidate as migrated / intentionally opaque / developer-only / OS-owned / unreachable. Review each computed JSX and generic metadata producer manually. Require no reachable unmigrated product English, complete key/parameter/plural tests, Arabic native copy review and Hermes Intl validation. Catalog counts alone do not close this gate.
8. **Separate Arabic/RTL activation approval.** Only after closure, implement the real language selector and verified runtime direction using the existing foundation. Test English on Arabic-device settings and Arabic on English-device settings, native/web tabs, gestures/back, text inputs, accessibility focus, large type, recovery overlays, restart and all six theme/language combinations. Never infer this approval from Phase 4A.

## Data and technical constraints

- Fixed keys use `translate(language, key)`; parameterized keys use `formatMessage(language, key, params)` or a typed `MessageDescriptor` with `translateMessage`. There is no positional interpolation or ICU syntax. Parameters are named, strings stay literal (including braces and `$&`), and numeric parameters are localized once at display time. Raw ISO dates/version strings/user content stay strings unless the caller deliberately formats a date for display.
- English has one/other cardinal forms; Arabic requires zero/one/two/few/many/other. Natural zero/one/two sentences may omit the printed count but still require a numeric `count` for selection. Parameter unions must match across catalogs; all forms must be nonempty and use only declared names. Fractional cardinals use Intl selection; negative/non-finite message counts are rejected.
- Display locales are explicit `en-US`/`ar-EG`; Gregorian calendar is explicit; English digits are Latin and Arabic digits Arabic-Indic. Number/date/plural formatters are cached per supported language. Local-date formatting uses validated local parts, never `new Date('YYYY-MM-DD')` UTC interpretation. The display range helper repeats full endpoints to avoid engine-dependent `formatRange` availability. Input normalization is an unused opt-in helper, not a validator change.
- Missing translations diagnose and fall back to canonical English; invalid parameters/unknown keys return a safe generic English message by default. Strict test translators throw typed diagnostic codes. Development diagnostics log codes only, not user parameter values. New descriptors do not persist or translate native `Error.message` content.
- No `expo-localization`, dependency or native config is added. Phase 4A needs no native rebuild. Later locale discovery, OS per-app language metadata or native layout changes could require separate review/build work; none is approved here. Hermes glyph/Intl behavior, Arabic grammar and actual RTL layouts remain physical acceptance gates.
